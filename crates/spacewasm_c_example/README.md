# SpaceWasm example C API

A C-linkable build of the [`spacewasm`](../..) WebAssembly 1.0 interpreter.

This directory is a **C-ABI test runner**, not a library. It intentionally has
**no** dependency on [`spacewasm_c_api`](../spacewasm_c_api) (that crate is a
standalone `no_std` staticlib whose baked-in `#[panic_handler]` cannot be linked
into a `std` crate). Instead this crate builds `spacewasm_c_api` as a static
library with `cargo`, then compiles and runs the C programs under `examples/`
against the resulting archive and committed header — proving the library links
and executes end-to-end with only C-supplied hooks.

## Layers

- `spacewasm`: Core `#![no_std]` interpreter (pure Rust).
- `spacewasm_c_api`: FFI support + the `spacewasm_*` C entry points. This crate
  is compiled to `libspacewasm_c_api.a` (`crate-type = ["staticlib", "rlib"]`).
  Under its default features it also emits the global allocator symbols and the
  `#[panic_handler]` that delegates to a C-defined `spacewasm_panic`.
- `spacewasm_c_example` (this crate): a `std` test harness that builds the
  staticlib and links/runs the C examples against it.

The interpreter capacities `MAX_CONTROL_FRAMES` and `MAX_STACK_DEPTH` are chosen
when `spacewasm_c_api` compiles, from an environment variable (see below), because C
cannot supply const-generic parameters. The maximum number of compiled code
pages is instead a runtime argument: the `max_code_pages` field of
`spacewasm_compiler_options_t`, passed to `spacewasm_new`. The heap allocator C
cannot supply is registered at runtime via `spacewasm_set_global_allocator` (the
default `provide-global-allocator` feature), and guest linear-memory allocators
are created from C callbacks with `spacewasm_allocator_new`.

### Changing the configuration

The maximum number of code pages is passed at runtime as the `max_code_pages`
field of `spacewasm_compiler_options_t` given to `spacewasm_new`, so it needs no
rebuild.

The remaining capacities are compile-time constants generated by
[`spacewasm_c_api`'s `build.rs`](../spacewasm_c_api/build.rs) via  configuration file which can be specified with the environment variable `SPACEWASM_CONFIG`, each with a default:

| Constant                        | Default |
| ------------------------------- | ------- |
| `MAX_CONTROL_FRAMES`            | 64      |
| `MAX_STACK_DEPTH`               | 256     |
| `GLOBAL_ALLOCATOR_MAX_PAGES`    | 16      |
| `GLOBAL_ALLOCATOR_PAGE_SIZE`    | 8192    |

To set them for the build, add them to a `.rs` source file as `pub const` values and then include that config file with the `SPACEWASM_CONFIG` environment variable before rebuilding:

```sh
SPACEWASM_CONFIG=my_config.rs cargo build -p spacewasm_c_api
```

The C header and ABI are unchanged (handles are opaque), so C callers do **not**
recompile. The capacities cannot be set from C at runtime; that is why the
integrator layer exists.

### Flight builds

The C examples register a `libc`-backed heap allocator (`aligned_alloc`/`free`)
so they run on a host for testing. A flight integrator supplies a deterministic
allocator through the same `spacewasm_set_global_allocator` /
`spacewasm_allocator_new` callbacks and compiles with `panic = "abort"` (a Rust
panic crossing the FFI boundary in `no_std` is undefined behavior). The
`spacewasm_c_api` staticlib is already `#![no_std]` with `panic = "abort"`.

## Usage from C

See [`examples/ctest.c`](examples/ctest.c)

## Building & testing

```sh
cargo build -p spacewasm_c_api                # produces libspacewasm_c_api.a (+ rlib)
cargo test  -p spacewasm_c_example            # builds the staticlib, then C link/run tests
```

`tests/c_abi.rs` compiles the C programs under [`examples/`](examples) —
[`ctest.c`](examples/ctest.c) (a minimal `add(20, 22)` load-and-invoke) and
[`ctest_suite.c`](examples/ctest_suite.c) (the full ported ABI suite: modules,
streaming, host functions, error paths, statistics, and the no-leak lifecycle
check) — against the header
([`../spacewasm_c_api/include/spacewasm.h`](../spacewasm_c_api/include/spacewasm.h))
and the freshly built `libspacewasm_c_api.a`, then runs them (skipped if no C
compiler is present). The Rust-driven unit tests that drive the `extern "C"`
functions directly live in
[`../spacewasm_c_api/src/tests.rs`](../spacewasm_c_api/src/tests.rs).

### Regenerating the C header

[`include/spacewasm.h`](../spacewasm_c_api/include/spacewasm.h) is generated from
the Rust source by `spacewasm_c_api`'s build script (cbindgen) and committed. To
refresh it after changing the C surface, build `spacewasm_c_api` with the
`codegen` feature:

```sh
cargo build -p spacewasm_c_api --features codegen
```

Ordinary builds do not need the feature (or cbindgen); they consume the
committed header as-is.
